## 设计决定

### D1 · 谁能定案

**只有持管理密钥的发起人。** 理由：定案是「拍板」，误触代价高；而且发起人是张罗的人，让他收口符合直觉。

代价：如果发起人不在，别人定不了。可接受 —— 这个产品的瓶颈从来是「有人不填」，不是「有人不肯定」。

### D2 · 核心成员谁来标

**发起人在结果页标记，即时重排。**

我考虑过三个方案：

1. **参与者自己勾「我必须到」** —— 零权限设计，最简单。但「核心」是群体共识，让个人自封不成立，四个人全勾就等于没勾。
2. **创建活动时标记** —— 那时人还没加入，做不到。
3. **发起人在结果页标记** ✅ —— 那时人都填完了，而且**改完立刻能看到方案怎么变**，反馈最直接。发起人本来就有管理密钥。

所以：结果页对发起人显示一个小开关，勾上就调 API 重排。其他人看不到这个开关。

### D3 · 日历导出怎么生成

**前端生成 `.ics` 文件，不用后端。**

好处：零后端改动、零存储、离线也能用。

格式选择：**全天事件**（按天粒度时）。`DTSTART;VALUE=DATE:20251005` —— 手机日历会显示成一条贯穿整天的条，比定一个「下午 3 点」的准确时刻更符合「出去玩几天」的语义。

时间用 **UTC 表示**（`DTSTART:...Z`），不写 VTIMEZONE。手机拿到后会按本地时区显示，跨时区也不会错。

### D4 · 出行卡长什么样

一张能直接截图发群里的东西：**活动名 / 时间 / 地点 / 谁去**。

配一个「复制成文字」按钮 —— 因为群里最实际的用法是发一段文字，而不是发图。

### D5 · 已定案之后结果页怎么变

定案前：方案列表全展开，发起人每张卡片上有个「定这个」按钮。
定案后：顶部一条定案横幅（出行卡入口），方案列表折叠成「看看其他方案」。

**不隐藏其他方案** —— 万一要改主意，路还在。

## 实施过程中的两处设计改动

### 改动一：删掉「核心成员模式」开关

原设计要**两个开关同时打开**才生效（创建时勾「核心成员模式」+ 结果页标记人），
而发起人在创建活动时根本不知道会不会用到核心成员 —— 等于埋了个死胡同。

改成只有一个概念：**标了谁，谁就是核心；一个都没标，就等于没有核心。**
创建页的开关删掉。`planner.ts` 里 `blocked` 的判断从
`coreOnly && cores.length > 0 && ...` 简化为 `cores.length > 0 && ...`。
数据库的 `core_only` 列保留（去掉要写迁移，收益不大），但永远存 false。

### 改动二：区分「时间窗口」和「行程长度」

**运行中发现的问题**：结果页显示「10月5日 – 10月7日 · 莫干山」，
点定案后卡片却变成「10月5日 – 10月6日 共 2 天」——前后对不上。

根因是窗口合并：莫干山只要 2 天，10/5–10/6 和 10/6–10/7 人群相同，
被合并成「10月5日 – 10月7日」。**合并没有错**（否则会冒出 5 个几乎一样的莫干山选项），
**错的是一个 2 天的行程显示成了 3 天的范围**。

修法：`FinalizedPlan` 同时记 `startSlot/endSlot`（窗口）和 `daysNeeded`（行程长度），
卡片显示成「10月5日 – 10月7日　**玩 2 天，任选**」，并附一句
「这几天里任意连续 2 天都能成行，具体哪两天群里定一下」。

日历文件要的是具体日期，所以按窗口的**最早 N 天**排 —— 先占上位置。

## 已知的坑（上次踩过的，这次别再踩）

1. **`run_worker_first` 加 `/e/*` 就必须同时实现放行**，否则朋友点链接看到 JSON 404
2. **部署必须走 `npm run deploy:pages`**，不能用 `npm run deploy`（`workers.dev` 国内被墙）
3. **时间戳不要手写数字**，用 `Date.UTC(...)` 算 —— 手写差 8 小时时断言看不出来，只有界面上才暴露
4. **拖拽 / 连续操作要用组件内部的即时值**，不能读 props（React 闭包陷阱）
5. **接口响应里绝不能带 `token` 或 `adminKey`** —— 冒烟测试里已有断言盯着
