日期：2026-09-15
状态：已确认

## 0. 名字

**何时何地**（`heshihedi`）

字面覆盖产品的两个维度：**何时 = 时间，何地 = 目的地**。

更有意思的是——**这个名字恰好把核心洞察写进去了**。产品要回答的从来不是"大家什么时候有空"和"大家想去哪"这两个独立的问题，而是**它们合在一起的那个答案**。去云南要 5 天、去露营只要 2 天，时间和地点是绑死的（详见 §3.1）。一个叫「何时何地」的产品，天然就该给出「何时 + 何地」合在一起的答案。

名字记法：四个字，成语式结构，不容易念错、不容易撞名，长辈和同事群里也不需要解释。

---

## 1. 一句话

**一群朋友想出去玩，各自填上「我什么时候有空」和「我想去哪」，系统直接算出几个能执行的方案。**

---

## 2. 问题与定位

### 2.1 真实痛点

几个朋友约着出去玩，商量时间是纯消耗：在群里一句一句对，"你周六行吗""我周六要加班""那周日呢"……循环几十轮。目的地同理，"我想去云南""太远了吧""那去周边？"。

这个过程有三个具体的痛点：

1. **对时间要来回问几十轮** —— 没有结构化的载体，全靠聊天记录对齐
2. **目的地和假期长度是绑定的，但聊天里说不清** —— 去云南要 5 天，去露营只要 2 天。大家嘴上说"都行"，实际是"我没那么多假"
3. **永远有人不表态，而没人知道该催谁** —— 约不成的头号杀手不是"没时间"，是"有人一直没回"

### 2.2 定位

**先自己用，但按"将来能公开"的标准写代码。**

- 只部署给自己和朋友用，不做账号体系、不做推广
- 但数据模型、无状态链接分享、代码结构都按可公开的标准写
- 哪天想公开，加一个首页和一份条款即可，不用重写

### 2.3 技术成本约束

**除 token 外零花费。**

- 部署在 Cloudflare 免费层（Workers + D1）
- 免费额度对"几个朋友用"是完全过剩的：一个活动约消耗 50 次页面请求 + 500 次 API 调用，而免费层是 10 万请求/天、500 万行读/天
- **关键安全性**：Cloudflare 免费层超额是**停止服务**（查询报错到次日 UTC 零点），**不会自动扣费**。必须手动进后台升级才会开始计费
- 域名可选（约 ¥70/年），不买就用 `*.workers.dev` 子域名

## 3. 核心洞察

### 3.1 时间表和地点表不能分开算

这是整个产品的立身之本。

**反例**：四个人，两个目的地，国庆前后

| 人 | 想去 | 需要的天数 | 有空的日期 |
|---|---|---|---|
| 小王 | 云南 | 5 天 | 10/1–10/7 |
| 小李 | 云南 | 5 天 | 10/1–10/7 |
| 小张 | 莫干山露营 | 2 天 | 10/5–10/7 |
| 小赵 | 莫干山露营 | 2 天 | 10/1–10/7 |

- **分开算**：时间表 → "10/5–10/7 全员有空，10/1–10/4 差一个人"；地点表 → "云南 2 票 : 莫干山 2 票（平票）"。拼起来是"那就 10/5–10/7 全员齐了，去云南或莫干山"——**但这根本不可行**：云南要 5 天，这三天去不了；而且云南只有 2 个人投过。
- **交叉算**：直接列出可行方案 ——

| 方案 | 时间 | 地点 | 能来的人 | 人数 |
|---|---|---|---|---|
| A | 10/1–10/5 | 云南（5天） | 小王 ✓ 小李 ✓ 小张 ✕ 小赵 ✕ | 2 |
| B | 10/5–10/7 | 莫干山（2天） | 小王 ✕ 小李 ✕ 小张 ✓ 小赵 ✓ | 2 |
| **C** | **10/5–10/7** | **莫干山（2天）** | **全员 ✓** | **4** 🏆 |

**两张表都没错，拼起来是错的。** 因为"愿意为哪个地方花多少时间"这根线，在拆表的时候被剪断了。

### 3.2 优雅之处：参与者不需要多填任何东西

参与者只做两件事：**涂自己的空闲时段**、**选想去的地方**。

系统从时间网格**自动推导出「他最多能连续空几天」**，再和「去云南要 5 天」对上。**输入没变复杂，输出从两张表变成了几个能直接执行的方案。**

### 3.3 竞争位置

- **开源侧完全空白**：成熟的开源项目只有时间协调（Rallly 5.2k★、timeful.app 1.7k★），目的地投票只有 0–2★ 的仓库
- **商业侧没人做透**：Howbout、CrewsCanvas 试过，但都没有把交叉计算做出来
- **分开算 = 一个更好的 Doodle**（市面十几个）；**交叉算 = 解决一个没人解决过的问题**

## 4. 用户与角色

| 角色 | 是谁 | 需要做什么 | 需要注册吗 |
|---|---|---|---|
| **发起人** | 张罗这次活动的人 | 建活动、发链接、看进度、催人、定案 | 不注册，凭「管理密钥」管理自己的活动 |
| **参与者** | 群里的朋友 | 点开链接、填名字、涂时间、选目的地 | **完全不注册** |

**免注册是底线。** Doodle 早期靠"建投票和投票都不注册"做到约 3000 万月活，后来改成建投票要账号、免费版插广告、"自动提醒"做成付费功能，用户量崩了（Aalto 大学等机构弃用）。**瓶颈是受邀者，不是组织者。**

## 5. 功能范围

### 5.1 第一期（MVP）—— 跑通完整闭环

**A. 发起活动**
- 活动名称
- 大致时间范围（起止日期）
- 时间粒度：按天 / 按半天（默认按天）
- 是否收集目的地
- 是否启用预算维度
- 是否启用「核心成员」模式
- 生成活动链接

**B. 参与者填写（免注册）**
- 输入名字（自动记住，可改）
- 时间网格涂抹：三态（可以 / 勉强 / 不行），支持拖拽连涂
- 目的地：从已有提名中选，或自己提名一个新的
- 每个目的地标注：需要几天、大致预算
- 对每个目的地表态：想去 / 都行 / 不想去
- 提交后可凭 token 回来修改

**C. 结果页**
- 顶部进度条："已填 4/6" + 一键催剩下的人
- **方案列表**：按人数排序，冠军方案高亮
- 每个方案显示：时间窗口 + 目的地 + **谁能来、谁不能来（点名）**
- 点开方案 → 展开热力图，看每个时段的可用人数
- 未填人员的明确提示

**D. 定案与分享**
- 一键锁定最终方案
- 生成出行卡（时间、地点、人员）
- 复制到群里的话术
- **导出 .ics 日历文件** —— 朋友点一下加进手机日历，到时间由系统提醒

**E. 发起人管理**
- 凭管理密钥查看/管理自己的活动
- 删除活动

### 5.2 第二期 —— 体验与效率

- **玻璃质感视觉与动效**（按第 10 节规范实现）
- **历史复用 / 常用群组**：记住常用的一群人，下次一键拉进来
- **跨时区支持**（数据层已预留，只差界面）
- 活动模板

### 5.3 明确不做（非目标）

- ❌ 行程规划（订机票、排每日行程）—— 那是 Wanderlog 的地盘，不是这个产品要解决的问题
- ❌ 费用分摊记账 —— Splitwise 的地盘
- ❌ 聊天/评论区 —— 会增加复杂度，且和微信群重叠
- ❌ 账号体系与登录 —— 参与者永远免注册
- ❌ 微信小程序 —— 微信 WebView 会拦截非白名单跳转，分享链接的参数也容易被吃掉；H5 才是对的路
- ❌ 主动推送通知 —— H5 做不到，用 .ics 日历提醒替代

## 6. 核心概念

| 概念 | 含义 |
|---|---|
| **活动 Event** | 一次约人。有一个时间范围、一群参与者、若干目的地 |
| **时段 Slot** | 时间轴上最小的可涂单位。按天粒度时 = 一天；按半天粒度时 = 上午/下午 |
| **可用性 Availability** | 某人对某个时段的状态：可以(2) / 勉强(1) / 不行(0) |
| **目的地 Destination** | 一个候选去处。自带「需要几天」和「大致预算」 |
| **意愿 Vote** | 某人对某个目的地的态度：想去(2) / 都行(1) / 不想去(0) |
| **方案 Plan** | 一个「目的地 × 时间窗口」的组合，附带能来的人。**这是产品的最终产出** |
| **管理密钥 Admin Key** | 发起人的身份凭证。存在浏览器里，可导出备份 |

| `finalized_plan` | TEXT | 定案后的方案 JSON（可为空） |

### participants

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | |
| `event_id` | TEXT FK | |
| `name` | TEXT | 显示名 |
| `token` | TEXT | 认领/修改用的凭证，放在链接里 |
| `is_core` | INTEGER | 0/1，是否核心成员 |
| `availability` | BLOB | **位图**：每格 2 bit，见下 |

**`availability` 位图编码**：每个时段占 2 bit（0=不行，1=勉强，2=可以）。按天粒度、30 天范围只需 8 字节；90 天也只要 23 字节。存成 BLOB，读写都极快，比存 JSON 数组省一个数量级。

|---|---|---|
| `id` | TEXT PK | |
| `event_id` | TEXT FK | |
| `name` | TEXT | 地名 |
| `days_needed` | INTEGER | 需要几天 |
| `budget_level` | INTEGER | 1–3 档（低/中/高），budget_enabled 时启用 |

### votes

| 字段 | 类型 | 说明 |
|---|---|---|
| `participant_id` | TEXT FK | |
| `destination_id` | TEXT FK | |
| `level` | INTEGER | 0=不想去 / 1=都行 / 2=想去 |
| PK | (participant_id, destination_id) | 复合主键 |

### 匿名配置（发起人可配）

活动级别一个字段 `anonymity`：`open`（全实名）/ `vote_anonymous`（时间实名、目的地意愿匿名）。

- `open`：结果页显示每个人的具体态度
- `vote_anonymous`：目的地意愿只显示汇总（"有 2 人不想去"），不点名；时间部分仍然实名（否则无法催票、无法知道谁能来）

## 8. 核心算法：交叉方案矩阵

这是整个项目技术含量最高的一块。

### 8.1 输入

- N 个参与者的可用性位图
- M 个目的地，每个带 `days_needed`
- 活动的时间范围（切成若干 slot）

### 8.2 步骤

**第 1 步：展开时间轴**
把 `range_start` 到 `range_end` 按 `granularity` 切成 K 个 slot。

**第 2 步：算每个人的「可行窗口」**
对参与者 `i` 和目的地 `d`（需要 `n_d` 天 = `n_d / granularity` 个 slot）：

- 找出所有满足「连续 `L` 个 slot 中，**没有一格是"不行"**」的窗口
- 窗口长度 `L ≥ n_d_slots`
- 记录每个窗口的「勉强格数量」`weakness`

> **注意**：这里放开了一个口子 —— 窗口内**允许有"勉强"格**。理由：真实场景里"我那天可能有点事"不该直接判死。但"勉强"要在排序时被惩罚。

**第 3 步：枚举窗口（避免组合爆炸）**

朴素做法是枚举所有起止点，O(K²)。优化：**只用「某个人的可用段边界」作为窗口起点候选**。因为任何最优窗口的起点，一定落在某个人的可用段起点上（否则往前挪一格不损失任何人）。这样候选窗口数是 O(总边界数)，在真实场景里很小（30 天内每人最多几个可用段）。

**第 4 步：算每个 (目的地, 窗口) 组合**
对每个目的地 `d` 和每个候选窗口 `w`：

```
能来的人 = { i : w 完整落在 i 对 d 的某个可行窗口内 }
愿意去的人 = { i : votes[i][d] ≥ 1 }
成行的人 = 能来的人 ∩ 愿意去的人
```

- **核心成员模式**：若 `core_only` 开启，先要求所有 `is_core` 的人都在成行集合里，否则该方案降级标记
- **预算维度**：若 `budget_enabled`，记录成行者的预算档位分布，若跨度过大给出提示

**第 5 步：排序**

```
主排序：成行人数（降序）
次排序：核心成员覆盖度（core_only 时）
三次排序：- 总"勉强"格数（升序，越少越好）
四次排序：预算集中度（budget_enabled 时）
五次排序：时间窗口更早（升序）
```

**第 6 步：去重与裁剪**

- **合并相邻窗口**：若两个窗口的人群集合完全相同且时间相邻，合并成一个
- **砍掉被支配的方案**：方案 X 被方案 Y 支配，当且仅当**同一个目的地 + 受阻状态相同 + X 的人全都包含在 Y 里且 Y 人更多**。
  能去 X 的人一定能去 Y，而 Y 人更多 —— X 没有提供任何 Y 没有的东西。
  **关键例外**：目的地不同就不构成支配。所以「另一个目的地的人少的方案」必须保留 —— 那是取舍的体现，删了就看不见了。
- **截断**：只返回 Top 6–8 个方案
- **保证多样性**：若 Top 方案全部指向同一个目的地，额外保留每个目的地各自的最优方案（让用户看到"如果换地方会怎样"）

**第 7 步：生成"差谁"说明**

对冠军方案，显式生成：
- `没空的`：因为时间不行而缺席的人 + 具体原因（"10/1 之前没假"）
- `不想去的`：因为投了"不想去"而缺席的人

**这是最体现产品价值的一步** —— 用户不该自己去对照谁缺席。

### 8.2.1 边界情况

| 情况 | 处理 |
|---|---|
| **某目的地需要的天数 > 活动时间范围长度** | 该目的地直接标记为"这段时间内去不了"，在结果页单独列出并说明原因，不参与方案枚举 |
| **某目的地 0 人投票** | 不在方案列表里出现；在"没人选的地方"折叠区展示，避免被无声丢弃 |
| **没有任何方案能凑齐 2 人** | 不返回空结果。退化为"个人时间表"，展示每个人的可用情况，并提示"这段时间内凑不出共同时间，建议扩大时间范围" |
| **参与者少于 3 人** | 跳过方案枚举，直接给一张并排对照表（人少时算法没有价值） |
| **所有人对某目的地都投"不想去"** | 该目的地被排除，并在结果页说明"已被一致否决" |
| **参与者一直没填** | 不算进分母；方案排序时以"已填人数"为基数，同时显式提示"还有 N 人没填，结果可能变化" |

### 8.3 复杂度

- 时间轴：O(K)
- 每人每目的地的可行窗口：O(K)
- 候选窗口数：O(B)，B = 总可用段边界数（真实场景 < 50）
- 每个窗口算人群集合：用位图 AND 运算，O(N/64)
- 总计：**O(B × M × N/64)**，实际规模下是毫秒级

### 8.4 时区处理（预留，第一期不启用）

- 所有时间以 **UTC 秒**存储
- 活动自带 **IANA 时区名**字段（不能只存偏移量，因为 DST 规则会变）
- 显示时用 `Intl.DateTimeFormat` 显式传 `timeZone` 转换
- 第一期只按 `Asia/Shanghai` 显示，但存储格式已就位

## 9. 页面与交互

### 9.1 页面清单

| 页面 | 路由 | 谁用 | 核心内容 |
|---|---|---|---|
| 发起页 | `/new` | 发起人 | 活动名、时间范围、粒度、开关项 |
| 填写页 | `/e/:id/fill` | **参与者（90% 的流量）** | 涂网格 + 选目的地 + 提交 |
| 结果页 | `/e/:id` | 所有人 | 进度催票 + 方案列表 + 热力图 |
| 定案页 | `/e/:id/final` | 所有人 | 出行卡 + 复制话术 + 导出日历 |
| 我的活动 | `/my` | 发起人 | 凭管理密钥管理的活动列表 |

### 9.2 填写页的交互细节（最关键的一页）

这是 90% 的人唯一会看到的页面，必须做到**零学习成本**。

- **拖拽连涂**：按下 → 划过 → 松开，一次涂一片。用 Pointer Events + `setPointerCapture`，`touch-action: none`
- **拖拽语义用 linear（按时间顺序）而不是 square（矩形框选）** —— 手机上矩形框选误触严重
- **每涂一格立刻有反馈**：放大 + 变色 + 轻微回弹
- **三态切换**：点一下是"可以"，再点是"勉强"，再点是"不行"（循环）
- **快捷操作**：「整个周末都可以」这类一键填充按钮
- **顶部进度**：显示"你还差 3 天没填"，避免有人填一半就跑了
- **就近保存**：不用点提交也不会丢（本地暂存），但提交后才计入结果
- **键盘可达**：roving tabindex + 方向键移动 + Shift 扩选（无障碍要求）

### 9.3 结果页的交互细节

- **冠军方案置顶高亮**，但不隐藏其他方案（用户要能看到取舍）
- **默认只展开前 3 个方案**，其余折叠成"还有 N 个方案 ▾"。列表短才看得下去，但一个都没丢
- **每个方案卡片直接写清"差谁"**，不用用户自己对照
- **点开方案展开热力图**，热力图用主色深浅表示人数，**并在格子里直接写出人数**。
  只靠颜色深浅是不可靠的：「3/4 人」和「4/4 人」在同一个色阶上几乎看不出区别，
  而且手机上根本没有 hover 可以补足。颜色是辅助，数字才是信息。
  格子里的数字只算「明确可以」的人，不把「勉强」算进去 ——
  显示「4 人」却只有 3 个人确定能来，是会误导人的。
- **催票按钮常驻**，显示"还有 2 人没填"并可一键复制催办话术

## 10. 视觉规范

**状态：已实现**（一期先用基础样式跑通功能，二期按本节实现材质与动效）。

### 10.1 设计方向

**透明玻璃 + 实体厚度 + 克制配色**，参考 Linear 的克制结构 + visionOS 的材质感。

### 10.2 配色（三个颜色，封顶）

| 角色 | 用途 | 说明 |
|---|---|---|
| **中性暖灰** | 背景、文字、边框 | 占全页 90% 面积，不出声 |
| **靛蓝（主色）** | CTA 按钮、热力图、选中态 | 全页唯一主色 |
| **琥珀（暖色）** | 只做"勉强可以"这一档状态 | 与主色形成冷暖对比 |

**关键决定：状态色不用绿/黄/红三个色相，热力图用主色的三个明度。** 热力图的深浅本来就靠明度读，用三个色相是画蛇添足。这样一屏里有颜色、有层次，但不眼花。

### 10.3 玻璃材质规范

**透明质感的前提：背后必须有东西。** 纯色平底上的玻璃看起来就是一块发白的塑料片。所以页面背景需要有**2–3 个柔和的色块**（用主色和暖色），玻璃透过它们才成立。

**厚度的三层结构**（缺一不可）：

1. **上缘受光棱** —— `inset 0 2px 0 rgba(255,255,255,.95)`。光从上方来，上缘最亮。这一道决定"它是玻璃"
2. **下缘背光棱** —— `inset 0 -3px 5px -1px rgba(41,37,36,.22)`。光穿过厚玻璃后在下缘变暗。**这一道决定"它有厚度"**，少了它玻璃就变成塑料片
3. **左右侧棱** —— `inset ±2px 0 2px -1px rgba(255,255,255,.6)`。侧面被照亮，才有体积而不是平面

**底部侧壁**：伪元素 `::before` 向下延伸 8px，模拟真玻璃侧面能看到的一小条玻璃壁。按下时压缩到 4px —— 这是"按下去"的实感来源。

### 10.4 性能约束（硬性）

玻璃和动效在中低端安卓机上很贵，**必须控制**：

1. **玻璃层全页最多 4 层**（顶部导航、主 CTA、浮动提示、底部操作栏），绝不满屏铺
2. **3D 视差只在结果页和定案页用**；填写页保持轻
3. **进页面先探测设备性能**，低端机自动降级为纯色 + 普通阴影
4. **检测 `prefers-reduced-motion`，直接关掉视差和浮动动画**
5. **动效只用 `transform` / `opacity`**（走 GPU 合成层），绝不对 `backdrop-filter` 本身做动画

**原则：好机器看到完整效果，差机器看到简化版，两个都不难看、都不卡。**

### 10.5 落地情况

| 规范 | 实现位置 |
|---|---|
| 背景色块（玻璃的前提） | `index.css` 的 `body::before`，两个色相的三个柔光斑 |
| 厚玻璃三层结构 + 侧壁 | `.glass` / `.glass-edge`（底部侧壁用伪元素，按下时压缩） |
| 贴边玻璃条（底部操作栏） | `.glass-bar` —— 贴屏幕边缘，没有下缘和侧壁，改成上缘受光 + 向上投影 |
| 实心主按钮的厚度 | `.btn-solid` —— 同一套三层结构，按下时侧壁从 8px 压到 3px |
| 果冻感格子 | `.cell-jelly` + `.cell-lv1/.cell-lv2`，**不用 backdrop-filter** |
| 动效 | `cell-pop` / `rise-in` / `plan-in`，全部只用 transform + opacity |
| 设备降级 | `src/client/lib/perf.ts` → `html.lite` / `html.reduced-motion` |

**实施中额外发现的一点**：降级要分两种，不能混为一谈。

- `lite`（弱设备 / 省流量）：关掉实时模糊，改用不透明近似色。**动效可以保留**
- `reduced-motion`（系统无障碍设置）：关掉动效。**玻璃可以保留**

一开始想合成一个开关，但这两件事的成因完全不同 —— 一个是性能，一个是用户偏好。
系统开了「减少动态效果」的用户，不代表他的设备跑不动玻璃。

### 10.6 技术选型（视觉）

- Tailwind v4（配置写进 CSS `@theme`）
- shadcn/ui（Radix 原语，无自带样式，便于套自己的材质）
- Motion（`motion/react`）做交互动效
- 网格用 **CSS Grid + Pointer Events**，**不要用 canvas 库**

## 11. 技术架构

```
浏览器（移动优先）
   │  同一域名，无 CORS
   ▼
Cloudflare Pages（高级模式 · _worker.js）
   ├─ Hono —— API 路由
   ├─ 静态资源 —— React SPA（回退到 index.html）
   └─ OG 卡片注入中间件（微信分享预览）
   │
   ▼
Cloudflare D1（SQLite）· Drizzle ORM
```

### 11.1 为什么是 Pages 而不是 Workers —— 一个必须记下来的坑

**`*.workers.dev` 在中国大陆被墙了。** `*.pages.dev` 没有。

这不只是"DNS 解析不到"，TCP 连接本身就失败：
`curl --resolve` 强行指定 Cloudflare 的 anycast IP 也连不上。
而 `api.cloudflare.com` 从同一台机器访问是通的 —— 所以**不是 Cloudflare 的网络问题，
是 `workers.dev` 这个名字被针对了**。

诊断时容易踩的坑：Cloudflare **不给未创建的 Pages 项目名做泛解析**，
所以未创建的项目名查询会返回 NXDOMAIN，看起来也像"连不上"。
判断方法是看 DNS 有没有解析出 `2606:4700:310c::` 开头的 Cloudflare 地址 ——
已存在的项目会解析出来，未存在的不会。

**结论：部署目标是 Pages，网址 `https://heshihedi.pages.dev`。**

### 11.2 Pages 高级模式的三个约束

用 `_worker.js`（高级模式）部署整个应用，必须注意：

1. **Worker 负责所有请求**，包括静态文件。`src/server/index.ts` 的 `notFound`
   里有一段 `ASSETS` 回退：非 API 请求交给静态资源，资源里找不到的
   （比如 `/e/xxx` 这种前端路由）再回退到 `index.html`
2. **Pages 不支持 `--config` 指定配置文件**，只认根目录的 `wrangler.jsonc`。
   而那份是给 `npm run dev` 用的 Worker 配置
3. **Cloudflare 的 Vite 插件会留一个配置重定向**（`.wrangler/deploy/config.json`），
   让 wrangler 去读 Worker 配置。那份配置带着 `run_worker_first` 和
   `assets.directory`，被 Pages 继承后会导致只有 `/api/*` 走到 Worker，
   其余请求去找静态资源却找错目录 —— **表现为整站 522**

   所以 `scripts/build-pages.mjs` 在部署前会删掉这个重定向，
   并把根配置临时换成 Pages 版（`wrangler.pages.jsonc`），
   部署完用 `try/finally` 换回来。

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | Cloudflare Workers | 免费层充裕，冷启动几乎为零，超额不扣费 |
| 后端框架 | Hono | 专为 Workers 设计，极轻，TypeScript 一等公民 |
| 前端 | Vite + React 19 | 轻、快、无 SSR 框架的魔法 |
| 样式 | Tailwind v4 + shadcn/ui | 官方支持 Vite，便于套自定义材质 |
| 动效 | Motion (`motion/react`) | 生态标准 |
| 数据库 | Cloudflare D1 + Drizzle | 免费层充裕，SQLite 足够 |
| 部署 | Wrangler | 一条命令 |

**为什么不用 Next.js on Cloudflare**：需要经过 OpenNext 适配层，构建慢、出问题难排查。对这个体量的项目，"没有魔法"比"资料多"更值钱。

**为什么不用 Vercel + Neon**：Vercel 免费版（Hobby）**明确禁止商用**，与"留后路"的目标直接冲突；Neon 免费层会休眠，朋友点开链接要等冷启动。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| **组合爆炸**：目的地 × 时间窗口数量失控 | 只用「可用段边界」作候选起点；合并相邻同人群窗口；只返回 Top 6–8；保证每个目的地至少留一个方案 |
